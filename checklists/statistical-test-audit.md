# Statistical Test-Audit Checklist

Use this checklist when explicitly asked to assess whether tests provide credible independent evidence for statistically, epidemiologically or longitudinally consequential behaviour. This is a bounded read-only audit, not CI, coverage analysis, ordinary code review or a package-wide test review.

## Boundary and selection

- [ ] Select 2–4 functions only and state why each is consequential. Prefer a shared primitive and a public interface that composes it when this makes the evidence chain clearer.
- [ ] State the exact audit boundary, including backend or interface paths that are excluded.
- [ ] Do not run tests or coverage, generate fixtures, update snapshots, modify code or tests, or open implementation work unless separately authorised.
- [ ] Do not browse externally unless a definition or reference check is separately authorised.
- [ ] Stop after the selected functions. Recommend separate follow-up work rather than expanding the audit.

## Implementation-first contract

Complete this section before reading the corresponding tests or assertions.

- [ ] State accepted inputs and types, output units and schemas, and invalid-input behaviour.
- [ ] State inclusion, exclusion, missing-code, `NA`, blank, non-finite and duplicate handling where relevant.
- [ ] Identify denominators, aggregation units, ordering assumptions, statistical definitions and conventions.
- [ ] Identify boundary and unavailable states, including zero denominators, empty inputs, bounds, truncation or refusal behaviour.
- [ ] Identify transaction, snapshot, rollback, repeatability and privacy/value-leak guarantees where relevant.
- [ ] Note surprising or non-standard conventions explicitly.

## Tests, fixtures and expected values

- [ ] Read the direct tests and only the fixture/helper code needed to understand them after recording the implementation contract.
- [ ] Trace each load-bearing fixture to its construction and confirm that its intended semantic edge is actually present.
- [ ] Identify whether expected values are literal or hand-derived, calculated through an independent oracle, generated by production logic, shared between implementations, or frozen by a snapshot.
- [ ] Treat backend parity and wrapper-to-core comparisons as correctness evidence only to the extent that their calculation paths are independent.
- [ ] Do not give extra credit for fixture size, assertion count, coverage or successful execution.

## Independent checks

- [ ] Manually derive a small number of load-bearing results from transparent fixture values without calling an equivalent package helper.
- [ ] Check consequential counts, missingness, denominators, directions, statistical conventions and edge states rather than object shape alone.
- [ ] For numeric summaries, consider finite and missing counts, mean or median, type-7 quartiles where applicable, sample variance or SD, fences and proportion denominators.
- [ ] For categorical summaries, consider declared and unexpected levels, zero-count levels, missing-code exclusion, and total-row versus observed-value denominators.
- [ ] For longitudinal summaries, consider period sets, retained/exited/entered direction, overlaps and unions, history aggregation, gaps or reappearance, duplicate keys and zero denominators.
- [ ] State the exact values independently checked and whether they agree with the assertions. Mark unavailable independent truth as `not verified`.

## Evidence classification

Classify each material assertion or group of assertions as one of:

- **Independent correctness evidence:** hand-derived literals, transparent fixtures, authoritative mathematical identities, or an oracle that does not reuse production internals.
- **Cross-implementation or parity evidence:** agreement between backends, wrappers or implementations; useful but not independently dispositive when logic is shared.
- **Contract or regression evidence:** schemas, types, ordering, errors, snapshots and stable presentation.
- **Coverage-only evidence:** execution, non-error or non-empty checks without a meaningful correctness oracle.

## Test-quality assessment

- [ ] Ask whether an important plausible implementation error could still satisfy the current tests.
- [ ] Check ordinary numerical correctness, boundary and degenerate cases, missingness, zero denominators, type preservation, invalid inputs and deterministic ordering where relevant.
- [ ] Check declared zero-count categories or timepoints, unsupported types, backend parity, snapshot behaviour, rollback/reuse, privacy/value leakage and explicit unavailable states where relevant.
- [ ] Look specifically for a numerator and denominator being wrong together, reversed longitudinal direction, sample/population convention drift, dropped zero-count levels, shared backend bugs, circular expected values and shape-only assertions.

## Audit record

For each function record:

- function and role;
- implementation contract reviewed;
- tests and fixtures inspected;
- independent calculations;
- evidence classification;
- strong coverage and plausible undetected errors;
- confidence and limitations;
- one conclusion: `correctness defect`, `important test weakness`, `minor test improvement`, or `no material concern`.

Do not manufacture findings to fill every class. End with the selected-function stop statement, checks not run, and any separately scoped follow-up recommendation. Independently derived expectations strengthen the evidence but do not make a same-agent audit organisationally independent.
